# タスク 2-3：家族の空き状況を取得する API

- ブランチ名: `phase2/2-3-busy-api`（最新の main から分岐）
- 作業前に読むもの: [AGENTS.md](../../AGENTS.md)（特に「絶対に守ること」1）、[docs/03-architecture.md](../03-architecture.md)（① 個人カレンダー（free/busy））、[docs/06-decisions.md](../06-decisions.md)（2026-09-29 の `freeBusy.query` のプライバシー境界）、[docs/19-busy-sharing.md](../19-busy-sharing.md)、[docs/18-personal-events.md](../18-personal-events.md)（`/week/personal` の形）、[docs/15-week-api.md](../15-week-api.md)
- **人間の確認が必要**（ほかのメンバーの個人カレンダーに関わる、プライバシーの核心）

## 目的

家族の大人それぞれについて、「予定がある時間帯」（開始と終了だけ）を返す API を作る。**このタスクは API まで。** 週ビューへの表示は次のタスク（2-5）で作るので、画面は変えない。

## プライバシー（最優先）

- ほかのメンバーについて返してよいのは、**予定がある区間の開始と終了だけ**。タイトル・場所・説明・参加者はもちろん、**カレンダーの ID・名前・件数・どのカレンダー由来か**も返さない（カレンダー ID はメールアドレスの形が多い）。複数のカレンダーの区間は、メンバーごとに1本にまとめてから返す。
- あるメンバーの空き状況は、**そのメンバー自身のトークン**で、**そのメンバーが空き状況に選んだカレンダー**（`member_calendars.include_in_busy`）だけを `freeBusy.query` して取得する。リクエストした人のトークンで、ほかの人のカレンダーを読まない。
- 追加スコープ（`calendar.freebusy`）に同意していない、またはカレンダーを1つも選んでいないメンバーについては、Google を呼ばない。
- 取得した区間は D1 に保存しない。サーバー側でキャッシュもしない。ログにも出さない。
- 漏れていないことを確かめるテストを必ず書く（下の「テスト」）。

## API（`familySecurityMiddleware` を通す。入出力は共有の zod スキーマ）

`GET /api/families/:id/week/busy?start=YYYY-MM-DD`

- 週の範囲は家族の週 API と同じ計算（`getWeekRange`）。`start` の検証と対応年の範囲も `/week/personal` と同じ。
- 未ログインは 401、その家族の active な大人のメンバーでなければ 404。
- 応答に含めるのは、その家族の active な大人のメンバー（`user_id` があるもの）全員。リクエストした本人も同じ形で含める。子どもは含めない。
- メンバーごとに、状態と区間を返す。

  | 状態 | 意味 | 区間 |
  |---|---|---|
  | `ready` | 取得できた | まとめた後の区間（0件のこともある） |
  | `not_shared` | 追加スコープに未同意、または空き状況に使うカレンダーを選んでいない | 空 |
  | `unavailable` | 取得に失敗した（トークンの失効、Google のエラー、選んだカレンダーの一部がエラーなど） | 空 |

- **`unavailable` を「予定なし」として扱わせない。** 状態で区別でき、区間は空にする。失敗の理由（再認証が必要、など）は応答に出さない。
- **1人の失敗が、ほかのメンバーの結果に影響しない。** 全体を失敗にするのは、リクエスト自体の問題（401・404・不正な `start`）と、想定外の内部エラーだけ。
- あるメンバーが選んだカレンダーのうち1つでもエラーなら、そのメンバーは `unavailable` にする（取得できた分だけを返さない。`freeBusy.query` は HTTP 200 でも、カレンダーごとの `errors` を返すことがある）。
- 区間は週の範囲で切り取り、重なる区間・端点が接する区間は1つにまとめる。まとめる処理は `src/shared/domain` か `src/shared/time` の純粋関数にする（2-4 で作った処理を使えるなら使う）。時刻は `Asia/Tokyo` のオフセット付きで返す。
- 家族カレンダー自体は、もし選択に残っていても問い合わせから除く。
- 応答は成功・失敗ともキャッシュ不可にする（`/week/personal` と同じ）。
- 家族の週 API（`/week`）と `/week/personal` は変えない。空き状況をそれらの応答に混ぜない。

## 対象範囲の外

- 週ビュー・「家族」タブなど、画面の変更（2-5 で行う）。クライアント側の API 呼び出しや query hook も 2-5 で作る。共有の zod スキーマだけは、このタスクで `src/shared/schemas` に置く。
- 共通の空きの計算を応答に含めること（2-5 で、クライアントが `getFreeWindows` に家族予定と合わせて渡す）。
- Danran が個人カレンダーに書き出した予定の差し引き（`mirrored_blocks`）。まだ書き出す機能がないので作らない。
- D1 のスキーマ変更。マイグレーションは追加しない。
- Google のアクセストークンの取得方法の変更（リクエストごとの更新は既知の課題で、このタスクでは直さない）。

## テスト

- **プライバシー**
  - Google の `freeBusy.query` の応答に余分な項目（タイトル、場所、説明、参加者など）が混ざっていても、API の応答に一切出ないこと。
  - 応答のどこにも、カレンダーの ID・名前・メールアドレスが出ないこと（複数のカレンダーを選んだメンバーで確認する）。
  - 各メンバーのカレンダーが、そのメンバー自身のトークンだけで問い合わされること（Google へのリクエストの Authorization と、本文のカレンダー ID の組み合わせを検証する）。
  - 問い合わせるのが `include_in_busy` のカレンダーだけであること（`display_enabled` だけのカレンダーは問い合わせない）。
  - 未同意・未選択のメンバーについて、Google が呼ばれないこと。
  - D1 に区間が保存されないこと。
- 状態：`ready`（区間あり・0件）、`not_shared`（未同意／未選択）、`unavailable`（トークン失効、Google の 5xx・403、カレンダー単位の `errors`、不正な応答）。1人が `unavailable` でも、ほかのメンバーが `ready` で返ること。
- 区間：重なり・接する区間の統合、週の範囲での切り取り、日またぎ、複数カレンダーの統合。
- 認可：未ログイン 401、非メンバー 404、子どもや pending のメンバーが応答に含まれないこと。
- 入力：不正な `start`、`start` の重複指定、対応年の範囲外。
- 既存のテストがすべて通ること。

## 受け入れ基準

- 家族の大人それぞれの「予定がある時間帯」が、開始と終了だけで返る。
- ほかのメンバーの予定の中身やカレンダーの情報が応答に含まれないことが、テストで保証されている。
- 1人の取得に失敗しても、ほかのメンバーの結果は返る。失敗したメンバーは「予定なし」と区別できる。
- 画面と D1 のスキーマに変更がない。
- `pnpm typecheck` / `lint` / `test` / `e2e` が通る。`pnpm db:generate` で差分が出ない。
