# タスク 3-1：繰り返し予定の作成

- ブランチ名: `phase3/3-1-routine-creation`（最新の main から分岐）
- 作業前に読むもの: [AGENTS.md](../../AGENTS.md)、[docs/01-concept.md](../01-concept.md)（「ルーティンは背景に」）、[docs/02-screens.md](../02-screens.md)（S4）、[docs/03-architecture.md](../03-architecture.md)（「繰り返し予定」、`routine_settings`、`event_meta`）、[docs/05-implementation-plan.md](../05-implementation-plan.md)（Phase 3）、[docs/16-event-editing.md](../16-event-editing.md)（単発の予定の作成。同じ考え方を使う）、[docs/15-week-api.md](../15-week-api.md)

## 目的

習い事や家事代行のような「毎週の予定」を、Danran から登録できるようにする。登録した予定は、家族カレンダー上の Google の繰り返し予定になり、週ビューではルーティンとして控えめに表示される。

## 対象範囲

- このタスクで作るのは、**作成・一覧（最小）・シリーズ全体の削除**まで。
- 次のタスクに回すもの：直近の回のチップ、「この回を休む」、「振替」（3-2）。祝日・年末年始・休園日のスキップ（3-3）。重複の検出（3-4）。シリーズの内容の編集（時間や曜日の変更）。
- 単発の予定の作成・編集・削除（1-8）は変えない。週ビューで繰り返し予定を選んだときの「繰り返し予定の変更は準備中」の案内も、このタスクではそのままにする。

## データ

- `routine_settings` テーブルを足す（docs/03 の合意済みの設計）。Drizzle のスキーマ → `pnpm db:generate` で**新しいマイグレーション**を作る。既存のマイグレーションは編集しない。
  - 持つもの：ID、家族 ID、カレンダー ID、Google の繰り返し予定の ID（`recurring_event_id`）、カテゴリ（`lesson` 習い事／`housework` 家事代行／`other` その他）、`skip_holidays`、`skip_new_year`、`affects_availability`、既定の担当のメンバー ID、作成・更新の時刻。
  - `skip_holidays` と `skip_new_year` は列だけ作り、既定は false。このタスクでは画面に出さず、何の処理にも使わない（3-3 で使う）。
  - 家族の削除に連動して消える。既定の担当のメンバーが消えたら、担当は空にする。`(calendar_id, recurring_event_id)` は一意。
- 予定のタイトル・時刻・曜日・対象メンバーは、これまでどおり Google の予定を正とし、D1 には保存しない。対象メンバー・担当・候補/確定は、単発の予定と同じく `extendedProperties.private` に入れる（繰り返しの各回に引き継がれる）。繰り返し予定は、常に「確定」で作る。

## API（`familySecurityMiddleware` を通す。入出力は共有の zod スキーマ）

共通：未ログインは 401、その家族の active な大人のメンバーでなければ 404。カレンダー ID は必ず DB の `families.family_calendar_id` を使う（クライアントから受け取らない）。Google への呼び出しはリクエストした本人のトークンで行う。変更系の検査（`X-Requested-With`、`Origin`、ボディサイズ上限）は、予定の作成 API と同じにする。

- `POST /api/families/:id/routines`
  - 入力：タイトル（1〜200 文字）、曜日（月〜日から1つ以上）、間隔（毎週／隔週）、開始日、開始・終了の時刻（同じ日の中。終日は対象外）、終了日（任意。なければ無期限）、対象メンバー（複数可、空は家族全員）、既定の担当（大人1人または未指定）、カテゴリ、`affectsAvailability`（既定 true）、`clientRequestId`（UUID）。
  - Google の `events.insert` で、RRULE 付きの予定を作る（`FREQ=WEEKLY`、`BYDAY`、隔週は `INTERVAL=2`、終了日があれば `UNTIL`）。**開始・終了には `timeZone: "Asia/Tokyo"` を必ず付ける**（Google は、繰り返し予定にタイムゾーンを要求する）。
  - **最初の回の日付**：Google は、開始日が選んだ曜日でなくても、開始日に1回目を作る。開始日は、「指定された開始日以降で、選んだ曜日に当たる最初の日」に直してから送る。この計算は `src/shared/domain` の純粋関数にし、`src/shared/time` を使って `Asia/Tokyo` で行う。
  - 二重作成の防止：単発の予定と同じく、家族 ID・ユーザー ID・`clientRequestId` から決まる予定の ID を使う。Google への作成が成功して D1 への保存が失敗した場合は、同じリクエストの再送で回復できること（Google 側は同じ ID、D1 は衝突を無視して保存）。
- `GET /api/families/:id/routines`
  - D1 の `routine_settings` と、Google の繰り返し予定の本体（タイトル、時刻、RRULE、対象メンバー）を合わせて返す。Google 側で消された・見つからないものは、一覧に「Google カレンダーで見つかりません」の状態として出す（D1 の行は消さない）。
  - 返す項目：ID、タイトル、曜日、間隔、時刻、開始日、終了日、対象メンバー、既定の担当、カテゴリ、`affectsAvailability`、状態。
- `DELETE /api/families/:id/routines/:routineId`
  - シリーズ全体を削除する（Google の繰り返し予定の本体を `events.delete`、D1 の行を削除）。Google 側ですでに消えている場合（404・410）も、D1 の行を消して成功にする。途中で失敗しても、同じ操作の再試行で回復できること。
  - `routineId` は D1 の ID。ほかの家族のものは 404。

### 週 API への反映

- `GET /api/families/:id/week` の各予定に `affectsAvailability`（真偽）を足す。繰り返し予定の回で、`routine_settings` の `affects_availability` が false のものだけ false。それ以外は true。
- 週末カードの空きタイムラインと「週末の1日」は、すでに `getFreeWindows` にこの値を渡せる作りになっている。`affectsAvailability` が false の予定が、埋まっている時間・共通の空きの計算から除かれることを確かめる。予定そのものは、これまでどおり表示する。

## 画面（`/routines`。いまは「準備中」）

- 下のタブバーの「繰り返し」から「準備中」の表記を外し、この画面を開く。
- **一覧**：繰り返し予定のカードを並べる。タイトル（対象メンバーの色の点）、ルール（例「毎週 火 17:00–18:00」「隔週 土 10:00–11:00」）、既定の担当（あれば「担当 （名前）」）、カテゴリ、`affectsAvailability` が false のものには「家族の空き判定には影響しない」。1件もないときは、何を登録する画面かの短い説明と「追加」ボタン。
- **追加**：ヘッダーの「追加」ボタンから、作成フォーム（予定の作成ダイアログと同じ作り・同じ部品）を開く。項目は API の入力のとおり。曜日は複数選べるチェックボックス。時刻の初期値は 17:00–18:00、開始日の初期値は今日。保存中は操作を無効にし、失敗時は入力を残して固定の日本語の案内を出す。未保存の入力があるときの PWA 更新の保留（`useReloadProtection`）は、予定の作成ダイアログと同じ扱いにする。
- **削除**：カードの「削除」から、画面内で確認してから消す（「この繰り返し予定を、これまでの回も含めてすべて削除します」）。
- 作成・削除のあとは、この画面と週ビュー（「週末の1日」も）に反映される。
- フィルタ（すべて／習い事／家事代行）は、このタスクでは作らない。

## 変えないもの

- 単発の予定の API と画面、週ビュー・「週末の1日」の表示（足すのは `affectsAvailability` の反映だけ）。
- 個人予定・空き状況の API と画面。
- 既存のマイグレーションファイル。
- スコープ（追加しない。家族カレンダーへの書き込みは、いまの権限でできる）。

## テスト

- ユニット（純粋関数）：最初の回の日付（開始日が選んだ曜日のとき・違うとき・複数の曜日・週をまたぐとき）、RRULE の組み立て（毎週・隔週・複数の曜日・終了日あり/なし）、ルールの表示文。
- API：
  - 作成：Google に送る本文（RRULE、`timeZone`、最初の回の日付、`extendedProperties.private`）、D1 の行、同じ `clientRequestId` の再送で二重に作られないこと、Google 成功・D1 失敗からの回復。
  - 入力の検証：曜日なし、終了が開始より前、終了日が開始日より前、タイトルの長さ、存在しないメンバー、子どもを担当にできないこと。
  - 一覧：Google 側で消えたものの状態、ほかの家族のものが出ないこと。
  - 削除：Google の 404・410 でも成功すること、再試行、ほかの家族のものは 404。
  - 認可：未ログイン 401、非メンバー 404、カレンダー ID をクライアントから受け取らないこと。
  - 週 API：`affectsAvailability` が正しく付くこと。
  - マイグレーション：新しいテーブルだけを作り、既存のテーブルを変えないこと。
- Playwright（API をモック）：一覧（0件・複数件）、追加（曜日の複数選択、隔週、検証エラー、保存失敗で入力が残る、連打）、削除の確認、タブバーの表記、週末カードで `affectsAvailability` が false の予定が共通の空きを減らさないこと、390px と 445px。
- 既存のテストがすべて通ること。

## 受け入れ基準

- 毎週・隔週の予定を登録でき、Google カレンダー上でも繰り返し予定として表示される。
- 登録した予定が、週ビューでルーティンとして表示される。
- 「家族の空き判定に影響しない」とした予定が、共通の空きを減らさない。
- 登録した繰り返し予定を、シリーズごと削除できる。
- `pnpm typecheck` / `lint` / `test` / `e2e` が通る。`pnpm db:generate` で差分が残らない。

PR を作成したらマージせずに止まること。
