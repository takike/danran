## 方針（2026-10-12 に人間が決定）

- プリントの読み取りに使う LLM は、**Google の Gemini API**（docs/03 は Anthropic を前提に書かれているので、直す）。モデルは **Gemini 3.8 Flash**。モデルの ID は環境変数 `LLM_MODEL` で指定し、コードに固定しない。
- 人間が、API キーを発行するプロジェクトが**有料の区分**であること（送った内容が製品の改善に使われない区分）を確認した。無料枠のキーでは使わない。
- **このタスクでは、LLM を呼ばない。** 写真を安全に保存して、本人たちが見られる・消せるところまでを作る。読み取り（4-2）、確認画面（4-3）、カレンダーへの登録（4-4）は、次のタスク。

## 目的

プリントをスマホで撮ると、家族だけが見られる場所に保存される。保存した写真は、家族の大人だけが開けて、いつでも消せる。

## 対象範囲

- 作るもの：撮影の画面、写真の縮小、アップロード、保存、一覧、表示、削除。
- 作らないもの：LLM の呼び出し、読み取り結果の表示・編集、カレンダーへの登録、予定への添付（`event_attachments`）、やることの生成、失敗時の再試行。

## データ

Drizzle のスキーマ → `pnpm db:generate` で**新しいマイグレーション**を作る。既存のマイグレーションは編集しない。既存の行は消さず、書き換えない。

- 新しいテーブル `attachments`、`import_jobs`（docs/03 の合意済みの設計に沿う）。
  - `attachments`：ID、家族 ID（家族の削除に連動して消える）、R2 のキー、種類（`image/jpeg`）、幅、高さ、バイト数、作成者、作成の時刻。
  - `import_jobs`：ID、家族 ID、`attachments` の ID、状態（`pending`／`extracted`／`failed`／`committed`。このタスクで使うのは `pending` だけ）、読み取り結果・エラー・モデル（このタスクでは空のまま）、作成者、作成の時刻。二重作成の防止に使う値（家族・作成者・`clientRequestId` から決める。一意）。
  - `event_attachments` は、このタスクでは作らない（4-4）。
- R2（バインディング `PHOTOS`）：キーは `families/{familyId}/imports/{jobId}.jpg`。**キーは、サーバーが決める。クライアントから受け取らない。API の応答にも含めない。**
- 保存するのは、縮小した写真だけ。元の写真、位置情報、撮影機器の情報は保存しない。

## 写真の縮小（クライアント。純粋な部分は関数に分けてテストする）

- `<input type="file" accept="image/*" capture="environment">` で撮影または選択する。
- 画面側で、**向きを写真の情報どおりに直してから**、長辺 2000px 以内に縮小し、JPEG（品質 0.8）に書き出す（`createImageBitmap` と canvas）。書き出し直すことで、位置情報などの付加情報（EXIF）を落とす。
- 縮小後のバイト数が上限（3 MB）を超えるときは、品質を下げて書き出し直す。それでも超えるときは、固定の日本語の案内を出して送らない。
- 画像として開けないファイルは、固定の日本語の案内を出して送らない。

## API（`familySecurityMiddleware` を通す。入出力は共有の zod スキーマ）

共通：未ログインは 401、その家族の active な大人のメンバーでなければ 404。ほかの家族の取り込み・写真は 404（docs/05 は「403」としているが、このプロジェクトの決まりに合わせて 404 にする。docs/05 も直す）。変更系の検査（`X-Requested-With`、`Origin`）は、既存の変更系 API と同じ。

- `POST /api/families/:id/imports`
  - 本文は、JPEG のバイト列そのもの（`Content-Type: image/jpeg`）。`clientRequestId`（UUID）を、クエリかヘッダーで受け取る。
  - 検査：`Content-Type`、バイト数の上限（3 MB。`Content-Length` だけを信用せず、実際に読んだ量で確かめる）、**中身が JPEG であること**（先頭のバイト列と構造を、純粋関数で確かめる）、幅と高さ（JPEG のヘッダーから読む。長辺 2000px 以内。クライアントの申告を信用しない）、**EXIF（APP1 の `Exif`）が含まれていないこと**（含まれていれば拒否する。縮小していない写真が、そのまま保存されるのを防ぐ）。
  - 家族ごとの上限：`pending` の取り込みは 20 件まで。超えたら、固定コードで拒否する。
  - 同じ `clientRequestId` の再送では、二重に保存せず、最初の結果を返す。
  - R2 に保存してから、D1 に行を作る。D1 の書き込みに失敗したら、R2 のオブジェクトを消す。R2 だけに残ったオブジェクトができない順序と後始末にし、テストで確かめる。
  - 応答：取り込みの ID、状態、作成の時刻、写真の ID・幅・高さ。
- `GET /api/families/:id/imports`
  - その家族の取り込みの一覧（新しい順。最大 50 件）。各項目：ID、状態、作成の時刻、作成者のメンバー ID、写真の ID・幅・高さ。
- `GET /api/families/:id/attachments/:attachmentId`
  - 写真のバイト列を返す。`Content-Type: image/jpeg`、`Cache-Control: private, no-store`、`X-Content-Type-Options: nosniff`、`Content-Disposition: inline`。
  - D1 の行で、その家族のものであることを確かめてから、R2 を読む。R2 のキーを、URL やクエリから組み立てない。
- `DELETE /api/families/:id/imports/:importId`
  - 状態が `pending`・`failed`・`extracted` の取り込みを消す（R2 のオブジェクト、`attachments`、`import_jobs`）。`committed` は、このタスクでは発生しない（発生したら拒否する）。
  - 同じ操作を2回送っても、同じ結果になること。R2 の削除に失敗したら、D1 の行は残して失敗を返す（写真だけが残って、消す手段がなくなるのを防ぐ）。

### ログとキャッシュ

- **写真のバイト列、R2 のキー、ファイル名を、ログに出さない。** エラーの応答にも含めない。
- PWA（Service Worker）が、`/api/` 以下の応答（特に写真）をキャッシュしないこと。いまの設定で保証されていることを確かめ、テストか docs で示す。保証されていなければ、キャッシュしない設定にする。

## 画面

- 下のタブバーの中央の「撮影」ボタンから「準備中」を外し、`/import` を開く。ログインしていて、家族の準備ができている利用者だけが見られる（「やること」の画面と同じ条件・同じ行き先）。
- `/import` の画面：
  - 見出し「プリントを取り込む」、説明（1〜2 行。「撮った写真は、家族の大人だけが見られます。読み取りは、次の更新で使えるようになります」）。
  - 主ボタン「プリントを撮影」（カメラが開く）と、控えめな「写真を選ぶ」（`capture` なしの入力）。
  - 送信中：縮小した写真のプレビューと「保存中...」。操作を無効にする。失敗したら、プレビューを残して、固定の日本語の案内と「もう一度送る」（同じ `clientRequestId` で再送する）。未保存の写真があるときの PWA 更新の保留は、予定の作成ダイアログと同じ扱いにする。
  - 保存した写真の一覧：サムネイル（認可つきの API から取得）、保存した日時、「読み取り待ち」の表示、「削除」（画面内で確認してから消す）。サムネイルを押すと、写真を大きく表示する（閉じるボタン、Esc、フォーカスの戻り）。
  - 0 件のときは、説明だけ。
- 一覧の query の鍵に、ユーザーと家族を入れる。ログアウト・アカウント切替・家族の切替で、前の一覧と写真を表示しない（表示用に作った URL は、切替時と画面を離れるときに解放する）。
- 操作のあとの取り直しは、裏で行う。**同じユーザー・家族のキャッシュがあれば、取り直しの間も表示したままにする**（読み込み中の表示に差し替えない）。

- 予定・やること・繰り返し予定のデータ。スコープ。Cron を足さない。
- デプロイ設定（`wrangler.jsonc` の R2 のバインディングは、すでにある。変えない）。CI/CD。

## テスト

- ユニット：JPEG の判定（正しい JPEG、PNG や HEIC を拒否、途中で切れたデータ）、幅と高さの読み取り、EXIF の検出、縮小後の寸法の計算（縦長・横長・正方形・もともと小さい画像）。
- API：
  - アップロード：保存されること（R2 のキーの形、D1 の行）、応答に R2 のキーが含まれないこと。種類の違い・上限超過（`Content-Length` を偽った場合を含む）・JPEG でない中身・大きすぎる寸法・EXIF つき、のそれぞれを拒否すること。
  - 同じ `clientRequestId` の再送で、二重に保存されないこと。家族ごとの上限。
  - D1 の失敗で、R2 にオブジェクトが残らないこと。
  - 一覧：自分の家族の分だけ。
  - 写真の取得：応答のヘッダー、**ほかの家族の写真が 404 であること**、未ログイン 401、存在しない ID。
  - 削除：R2 と D1 の両方から消えること、2回目も成功すること、R2 の失敗で D1 の行が残ること、**ほかの家族の取り込みを消せないこと**。
  - 変更系の検査。マイグレーション：新しいテーブルだけを作り、既存のテーブルと行を変えないこと。
- Playwright（API をモック、合成の画像。実在のプリントを使わない）：
  - 写真を選ぶ → 縮小されて送られること（送った本文が JPEG で、長辺 2000px 以内、EXIF なし）。保存後、一覧に出ること。
  - 送信の失敗と再送（同じ `clientRequestId`）、連打で二重に送られないこと。
  - 大きく表示、削除（確認、失敗時の案内）。
  - アカウントを切り替えたとき、前のアカウントの一覧と写真が表示されないこと。
  - 取り直しの間、一覧が表示されたままであること。
  - 390px と 445px で横にはみ出さないこと。操作できるものが 44px 以上であること。タブバーの「撮影」から開けること。
- 既存のテストがすべて通ること。

## 受け入れ基準

- スマホでプリントを撮ると、縮小された写真が保存され、`/import` の一覧に出る。大きく表示でき、削除できる。
- 保存された写真に、位置情報などの付加情報が含まれない。
- ほかの家族の写真と取り込みを、見ることも消すこともできないことが、テストで保証されている。
- R2 のキーが、API の応答・ログ・URL に出ない。
- LLM の呼び出しと、API キーを使うコードが入っていない。
- `pnpm typecheck` / `lint` / `test` / `e2e` が通る。`pnpm db:generate` で差分が残らない。
