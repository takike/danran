# タスク：予定の保存を速くし、失敗の原因を追えるようにする

- ブランチ名: `perf/event-save`（最新の main から分岐）
- 作業前に読むもの: [AGENTS.md](../../AGENTS.md)、[docs/16-event-editing.md](../16-event-editing.md)、[docs/11-google-calendar-client.md](../11-google-calendar-client.md)、`src/worker/google/calendar.ts`（`createGoogleCalendarClient` の第3引数 `reuseAccessToken`）、`src/worker/routes/events.ts`、`src/worker/index.ts`（全体のエラー処理）、`src/client/features/week/EventDialog.tsx`、`src/client/api/events.ts`、`docs/tasks/perf-routines-responsiveness.md`（同じ考え方で「繰り返し」を直したときの指示書）

## 背景

実機確認（2026-10-14）での指摘：

1. 予定の保存に時間がかかる。
2. 予定の追加で、「予定を保存できませんでした。時間をおいて再度お試しください。」が出て、保存できなかった。

調べて分かったこと：

- 予定のダイアログは、保存の応答のあと、**週の一覧の取り直しが終わるまで待ってから閉じている**（`EventDialog.tsx` の `await queryClient.invalidateQueries(...)`）。週の取り直しは Google への通信を伴うので、保存そのものより長くかかる。
- 予定の API は、Google を呼ぶたびにアクセストークンを取り直している（「繰り返し」は PR #35 で、1つのリクエストの中だけ使い回すようにした）。
- 2 の文言は、サーバーの応答が決まった形のエラーでなかったときに出る。サーバーの中で予期しない例外が起きたとき（全体のエラー処理が、エラーコードのない応答を返す）か、Cloudflare 側のエラーのとき。**原因は、まだ分からない。** いまは、全体のエラー処理が何もログに出していないので、あとから追えない。

## 目的

予定を保存したら、すぐにダイアログが閉じる。予期しない失敗が起きたときに、原因の種類をログで追える。

## 対象範囲

### 画面

- 予定の作成・編集・削除が成功したら、**応答を受け取った時点でダイアログを閉じる。** 週の一覧・空き状況・やることの取り直しは、裏で行う（待たない）。取り直しの間、週ビューを読み込み中の表示に差し替えない（いまの扱いのまま）。
- 保存した予定が週ビューに出るまでの間（裏の取り直しが終わるまで）、週ビューの上部に控えめな「更新中...」を出す（読み上げにも入れる。レイアウトを動かさない置き方にする）。取り直しに失敗したときは、いまの週ビューの再試行の扱いに乗せる。
- 保存の失敗時の扱い（入力を残す、同じ `clientRequestId` で再送する）は変えない。
- **応答が決まった形でないエラー**（エラーコードがない 5xx、本文が JSON でない、など）のときの案内を、「予定を保存できませんでした。保存されているか週の表示で確かめてから、もう一度お試しください。」にする（同じ `clientRequestId` で再送するので、二重には作られない。そのことを docs に書く）。

### サーバー

- `src/worker/routes/events.ts` の `createGoogleCalendarClient` を呼んでいるすべての箇所で、`reuseAccessToken: true` を指定する（作成・編集・削除）。トークンは、そのリクエストの処理の間だけ、メモリ上で使い回す。保存しない。リクエストをまたいで使い回さない。
- `src/worker/index.ts` の全体のエラー処理で、**エラーの種類だけ**をログに出す：HTTP メソッド、ルートの型（`c.req.routePath`。例 `/api/families/:id/events`。実際の ID を含めない）、エラーの名前（`err.name`。例 `TypeError`）、Google のエラーなら Google の HTTP ステータスと、このプロジェクトのエラーコード。**エラーのメッセージ、スタック、リクエストの本文、ヘッダー、URL の実際の値、トークン、予定の内容は出さない。** 応答の形は変えない。
- `events.ts` の中で、500 を返している箇所（`INTERNAL_ERROR`）も、同じ形でエラーの種類だけをログに出す。

## 変えないもの

- 予定の API の入出力、検証、Google への呼び出しの順序と数、やることへの追従。
- ほかのルートのトークンの扱い（週、個人予定、空き状況、家族、やること）。
- D1 のスキーマ、マイグレーション、スコープ、デプロイ設定（`wrangler.jsonc`。ログの保存の設定は、人間が判断する）。

## テスト

- API：
  - 予定の作成・編集・削除で、トークンの取得（Google の token エンドポイントへの通信）が、1回のリクエストにつき1回であること。401 のときは、取り直して1回だけやり直すこと（既存の挙動）。リクエストをまたいで使い回さないこと。
  - 予期しない例外のとき、ログに出るのがメソッド・ルートの型・エラーの名前だけで、ID・本文・メッセージ・トークンを含まないこと（ログを捕まえて確かめる）。応答の形が変わらないこと。
  - ほかのルートの、トークンの取得の回数が変わっていないこと。
- Playwright（API をモック。週の取り直しを2秒遅らせる）：
  - 作成・編集・削除の応答のあと、週の取り直しを待たずにダイアログが閉じること。取り直しの間、週ビューが表示されたままで、「更新中...」が出ること。届いたら、新しい予定が出て「更新中...」が消えること。
  - エラーコードのない 500 の応答で、新しい案内が出て、入力が残ること。もう一度押すと、同じ `clientRequestId` で送られること。
  - 390px と 445px。
- 既存のテストがすべて通ること。

## 受け入れ基準

- 予定を保存すると、週の取り直しを待たずにダイアログが閉じる。
- 予定の API で、トークンの取得が1回のリクエストにつき1回になる。
- 予期しない例外の種類がログに残り、ログに予定の内容・ID・トークンが出ない。
- `pnpm typecheck` / `lint` / `test` / `e2e` が通る。`pnpm db:generate` で差分が出ない。
