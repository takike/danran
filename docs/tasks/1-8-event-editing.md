# タスク 1-8：予定の作成・編集・削除

- ブランチ名: `phase1/1-8-event-editing`（最新の main から分岐）
- 作業前に読むもの: [AGENTS.md](../../AGENTS.md)、[docs/03-architecture.md](../03-architecture.md)（② 家族カレンダー、event_meta）、[docs/05-implementation-plan.md](../05-implementation-plan.md) の 1-8、[docs/15-week-api.md](../15-week-api.md)、[docs/02-screens.md](../02-screens.md)（S1、「予定の作成・編集」の記述、アクセシビリティ要件）

## 目的

週ビューから、家族カレンダーの予定を作成・編集・削除できるようにする。作成した予定は Google カレンダーにも出る。Google 側で時間を変えても、アプリの表示が追従し、付加情報（対象メンバー、担当、持ち物、候補/確定）は保持される。

## 対象範囲

- 対象は単発の予定だけ。繰り返し予定（`recurringEventId` または `recurrence` を持つもの）の編集・削除は Phase 3 なので、API は固定コードで拒否し、画面では「繰り返し予定の変更は準備中」と案内する。
- 添付、説明、場所、空き時間からの作成は含めない。
- 同時編集は後から保存したほうが勝つ（docs/06 に記録する）。

## API（すべて既存の securityMiddleware を通す）

- `POST   /api/families/:id/events`
- `PATCH  /api/families/:id/events/:eventId`
- `DELETE /api/families/:id/events/:eventId`

### 共通

- 未ログインは 401、その家族の active メンバーでなければ 404。家族が ready でなければ 409。
- カレンダー ID は必ず DB の `families.family_calendar_id` を使う（クライアントから受け取らない）。
- Google への呼び出しはリクエストした本人のトークンで行う。`sendUpdates` は `none`。
- 入出力は zod スキーマ（`src/shared/schemas`）で検証し、クライアントと共有する。
- 変更系は `X-Requested-With` と `Origin` の検査、ボディサイズ上限を既存の変更系 API と同じにする。

### 入力項目

- タイトル（必須、前後の空白を除いて1〜200文字）
- 日時：終日（開始日・終了日）または時刻指定（開始・終了、Asia/Tokyo）。終了は開始より後。終日の排他的終了日への変換など、日付計算は `src/shared/time` を通す。
- 対象メンバー（子どもを含む。0人以上）、担当（大人のメンバー1人または未指定）。どちらも、この家族の active メンバーの ID だけを受け付け、それ以外は 400。
- 持ち物（文字列の配列。上限件数と1件あたりの文字数上限を決める）
- 候補／確定

### 保存

- Google のイベントに `extendedProperties.private`（`danran="1"`, `members`, `assignee`, `status`, `source="manual"`）を書く。持ち物は `event_meta.items_json` に保存し、assignee / status / source も `event_meta` に同じ値を書く（docs/03 のとおり両方に保存）。
- 編集時は、既存の `extendedProperties` の未知のキーを消さない。Google カレンダーで直接作られた予定（danran マーカーなし）を編集したら、マーカーを付ける。

### 二重作成の防止

- POST はクライアントが生成した `clientRequestId`（UUID）を受け取り、そこから決定的に Google のイベント ID を作って insert に渡す。同じ `clientRequestId` の再送は、新しいイベントを作らず同じ結果を返す（Google が 409 を返したら既存のイベントを取得して続行する）。
- Google への書き込みが成功して D1 への書き込みが失敗した場合も、同じ `clientRequestId` で再試行すれば完了できるようにする。
- DELETE は、Google 側で既に消えている場合（404 / 410）も成功として扱い、`event_meta` の行を削除する。

### エラー

- Google 側の失敗は 1-6 と同じ分類の固定コードで返す（再ログインが必要、家族カレンダーにアクセスできない、一時的な失敗）。Google のエラー本文やトークンはレスポンスにもログにも出さない。

## 週 API の修正（このタスクに含める）

- `GET /api/families/:id/week` は、いま `event_meta` を家族の全件で読み込んでいる。その週に返すイベントの ID（と `recurringEventId`）に絞って取得するように直す。D1 のバインド数の上限を超えないよう分割する。

## 画面

- 週ビューに「予定を追加」ボタンを置く。各日からも、その日付を初期値にして追加できるようにする。
- 予定をタップすると編集画面が開く（繰り返し予定は上記の案内）。
- 作成・編集は全画面のダイアログ（ネイティブの `dialog` 要素）にし、ブラウザの「戻る」で閉じる。開いたときと閉じたときのフォーカス移動を正しく行う。
- フォーム：タイトル、終日の切り替え、日付、時刻、対象メンバー（色ドット付きの複数選択）、担当、持ち物（追加・削除）、候補／確定。すべて本物の `input` と `label` を使う。
- 初期値：日付は選んだ日（なければ今日）、時刻は次の正時から1時間。
- 削除は画面内の確認表示を挟む（`window.confirm` は使わない）。
- 保存・削除ボタンは同期 ref で二重送信を防ぎ、処理中は無効にする（招待発行ボタンと同じ考え方）。
- 成功したら週のクエリを再取得する。失敗時は入力内容を保持したまま、固定の日本語メッセージを出す。
- 文言は日本語、色や余白は `tokens.css` のトークン、タップ領域は 44px 以上。

## テスト

- API（fetch をモック）：作成・編集・削除の正常系、401 / 404（非メンバー）/ 409、入力検証（タイトル、時刻の前後、他の家族のメンバー ID、子どもを担当に指定）、同じ `clientRequestId` の再送で重複しないこと、Google 成功 → D1 失敗 → 再試行で完了すること、編集で未知の `extendedProperties` と持ち物が保持されること、削除の 404 / 410 を成功として扱うこと、繰り返し予定の拒否、オーナーでない大人が自分のトークンで実行できること。
- プライバシー：Google へのリクエスト先が家族カレンダーだけであること。
- 週 API：`event_meta` の絞り込み後も、1-6 の照合テストがすべて通ること。
- Playwright（API をモック）：追加・編集・削除の一連の操作、入力エラーの表示、連打しても送信が1回であること、「戻る」でダイアログが閉じること、繰り返し予定の案内、390px で横スクロールが出ないこと。
- 既存の E2E がすべて通ること。

## 受け入れ基準

- 作成した予定が Google カレンダーに出る（staging での確認手順を PR に書く）。
- Google カレンダー側で時間を変えても、アプリの表示が追従し、付加情報が保持される（自動テストで、Google 側の時刻変更後も `event_meta` と `extendedProperties` が読めることを確認する）。
- `pnpm typecheck` / `lint` / `test` / `e2e` が通る。`pnpm db:generate` で差分が残らない。
- スコープは追加しない。D1 スキーマの変更が必要になった場合は、理由を PR に書く。

PR を作成したらマージせずに止まること。
