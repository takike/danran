# タスク 5-1：やること（tasks）の API と、持ち物からの自動生成

- ブランチ名: `phase5/5-1-tasks-api`（最新の main から分岐）
- 作業前に読むもの: [AGENTS.md](../../AGENTS.md)、[docs/01-concept.md](../01-concept.md)、[docs/02-screens.md](../02-screens.md)（S5）、[docs/03-architecture.md](../03-architecture.md)（`tasks`、`event_meta`、「やること（tasks）の自動生成」）、[docs/05-implementation-plan.md](../05-implementation-plan.md)（Phase 5）、[docs/16-event-editing.md](../16-event-editing.md)、`src/worker/routes/events.ts`、`src/worker/db/schema.ts`

## 目的

予定にひもづく「やること」（持ち物の準備など）と、予定にひもづかない手動の「やること」を、家族で共有して管理するための API を作る。**このタスクは API と自動生成まで。** 画面（S5）は次のタスク（5-2）、週ビューとの連携は 5-3 で作るので、画面は変えない。

## 対象範囲

- 作るもの：`tasks` テーブル、一覧・作成・更新・削除の API、予定の持ち物からの自動生成、予定の変更・削除への追従。
- 作らないもの：画面、週ビューの表示、プリント取り込みからの生成（`source = import`。Phase 4）、重複からの生成（`source = conflict`。「〈習い事〉に欠席を連絡」。どの操作で作るかを決めてから、別のタスクにする）、通知。

## データ

Drizzle のスキーマ → `pnpm db:generate` で**新しいマイグレーション**を作る。既存のマイグレーションは編集しない。既存の行は消さず、書き換えない。

- 新しいテーブル `tasks`（docs/03 の合意済みの設計に沿う）
  - ID、家族 ID（家族の削除に連動して消える）、タイトル、期限（`due_at`、NULL 可）、期限の種類（`date` 日付だけ／`datetime` 日時／`none` なし）、完了の時刻（`done_at`、NULL 可）、担当のメンバー ID（NULL 可。メンバーが消えたら空にする）、`event_meta` の ID（NULL 可。`event_meta` の行が消えたら空にする）、発生元（`import`／`items`／`conflict`／`manual`。このタスクで使うのは `items` と `manual`）、発生元の参照（`source_ref`、NULL 可）、作成・更新の時刻。
  - 予定1件につき、持ち物からの自動のやること（`source = items`）は1件まで（`(event_meta_id, source)` に、`source = items` の行の一意制約）。
- **予定のタイトル・日時は、D1 に保存しない**（これまでどおり Google カレンダーを正とする）。自動のやることのタイトルは、固定の「持ち物を準備」を保存する。どの予定のものかは、`event_meta` へのひもづけで分かる。予定のタイトルと日時は、一覧を返すときに Google から取得して添える（下の「一覧」）。
- `event_meta` の行がない予定に、手動のやることをひもづけるときは、`event_meta` の行を作る（既存の作り方に合わせる）。

## 決まり（純粋関数にして `src/shared/domain/taskGeneration.ts` に置き、ユニットテストを付ける）

- **持ち物からの自動生成**：予定に持ち物が1つ以上あれば、その予定のやることを1件持つ。持ち物が0になったら、持たない。
- **期限**：自動のやることの期限は保存せず、予定の開始から決める。時刻指定の予定は「開始日の前日 20:00」、終日の予定は「開始日の前日 20:00」（どちらも `Asia/Tokyo`）。予定の日時が変われば、期限も変わる。
- 手動のやることの期限は、利用者が決めた値を保存する（なし／日付／日時）。
- 日付と時刻の計算は、`src/shared/time` のユーティリティを通す。

## API（`familySecurityMiddleware` を通す。入出力は共有の zod スキーマ）

共通：未ログインは 401、その家族の active な大人のメンバーでなければ 404。ほかの家族のやることは 404。変更系の検査（`X-Requested-With`、`Origin`、ボディサイズ上限）は既存の変更系 API と同じ。Google への呼び出しは、リクエストした本人のトークンで行う。カレンダー ID は DB の値だけを使う。

- `GET /api/families/:id/tasks`
  - その家族のやることを返す。既定は、未完了のものと、完了してから 14 日以内のもの。
  - 各項目：ID、タイトル、期限（種類と値）、完了の時刻、担当、発生元、ひもづく予定（あれば：予定の ID、タイトル、日時、対象メンバー、持ち物）。
  - **ひもづく予定の情報は、Google から取得する。取得は一覧全体で1回だけ**（ひもづく予定をまとめて取得できる方法で。件数・ページ数に上限を付ける）。予定ごとに1回ずつ呼ばない。
  - Google で見つからない予定（Google カレンダー側で消された）にひもづくやることは、「予定が見つかりません」の状態で返す（D1 は書き換えない。**GET では、D1 も Google も変更しない**）。
  - Google の取得に失敗したときは、やることの一覧は返し、予定の情報だけを「取得できませんでした」の状態にする。自動のやることの期限は、予定の情報が取れないときは「不明」として返す（「期限なし」とは返さない）。
- `POST /api/families/:id/tasks`（手動のやること）
  - 入力：タイトル（1〜200 文字）、期限（なし／日付／日時）、担当（大人のメンバー1人または未指定）、ひもづける予定の ID（任意）、`clientRequestId`（UUID。二重作成の防止に使う）。
  - 予定の ID を受け取ったときは、その予定が家族カレンダー上にあり、繰り返し予定の本体ではないことを、Google で確かめてからひもづける。
- `PATCH /api/families/:id/tasks/:taskId`
  - 変更できるもの：担当、完了／未完了（すべてのやること）。タイトル、期限、予定とのひもづけ（手動のやることだけ）。自動のやることのタイトル・期限を変えようとしたら、固定コードで拒否する。
  - 完了にしたときは完了の時刻を入れ、未完了に戻したら空にする。同じ操作を2回送っても同じ結果になること。
- `DELETE /api/families/:id/tasks/:taskId`
  - 手動のやることだけ削除できる。自動のやることは、固定コードで拒否する（持ち物をなくせば消える）。

### 予定の API への追従（`src/worker/routes/events.ts`）

- 予定の作成・更新で、持ち物が1つ以上になったら、自動のやることを作る（すでにあれば何もしない）。持ち物が0になったら、自動のやることを消す（完了済みでも消す）。
- 予定の削除では、その予定の自動のやること（`source = items`）は消す。手動のやることは残し、予定とのひもづけを外す（「予定に紐づかないやること」になる）。
- 予定の保存（Google と `event_meta`）が成功して、やることの更新が失敗した場合：予定の保存は成功として返し、同じ予定を次に保存したときに、やることが正しい状態に直ること（やることの有無を、毎回「あるべき状態」に合わせる作りにする）。
- 予定の API の入出力、検証、Google への呼び出しは変えない。

## 変えないもの

- 画面（このタスクでは、クライアントのコードを変えない。共有の zod スキーマだけ `src/shared/schemas` に置く）。
- 週 API、繰り返し予定、個人予定、空き状況の API。
- 予定の作成・編集の入出力と挙動（上の「追従」を除く）。
- 既存のマイグレーションファイル、スコープ、デプロイ設定。

## テスト

- ユニット（`taskGeneration.spec.ts`）：持ち物の有無と自動のやることの有無、期限（時刻指定・終日・月や年をまたぐ前日・0 時開始の予定）。
- API：
  - 一覧：未完了と、完了から 14 日以内のものだけが返ること。ひもづく予定の情報、Google の取得が一覧全体で1回であること、Google で見つからない予定・取得の失敗の状態、GET で D1 と Google が変更されないこと。
  - 作成：入力の検証、同じ `clientRequestId` の再送で二重に作られないこと、予定とのひもづけ（ほかのカレンダーの ID・存在しない ID・繰り返し予定の本体は拒否）、担当に子どもを指定できないこと。
  - 更新：担当と完了は全種類、タイトルと期限は手動だけ。完了と取り消しの繰り返し。
  - 削除：手動だけ。
  - 予定への追従：持ち物を足す・すべて外す・予定を削除する、のそれぞれで、自動と手動のやることが決まりどおりになること。やることの更新の失敗からの回復。
  - 認可：未ログイン 401、非メンバー 404、**ほかの家族のやることが見えず、変更・削除もできないこと**。変更系の検査。
  - マイグレーション：新しいテーブルだけを作り、既存のテーブルと行を変えないこと。
- 既存のテストがすべて通ること（予定の API のテストを含む）。

## 受け入れ基準

- 手動のやることを作成・更新・完了・削除できる。
- 予定に持ち物を付けると、その予定の「持ち物を準備」のやることが自動で1件でき、持ち物をなくすと消える。期限は、予定の日時から決まる。
- 予定を削除すると、自動のやることは消え、手動のやることは予定にひもづかない状態で残る。
- ほかの家族のやることを見ることも変更することもできないことが、テストで保証されている。
- 画面のコードに変更がない。
- `pnpm typecheck` / `lint` / `test` / `e2e` が通る。`pnpm db:generate` で差分が残らない。

PR を作成したらマージせずに止まること。
