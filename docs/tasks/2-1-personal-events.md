## 背景と順序の変更

Phase 1 の実機確認で、利用者から「自分の Google カレンダーの予定が Danran に出ない」という指摘があった。日常使いには、まず自分の予定が見えることが必要なので、Phase 2 の順序を次のように変える（docs/05 と docs/06 を更新する）。

1. **このタスク**：個人カレンダーの選択と、自分の予定の表示（元の 2-1 の一部と 2-6）
2. 家族の空き状況（free/busy、元の 2-2・2-3・2-4）
3. S2 週末の1日（元の 2-5）

## プライバシー（最優先）

- 個人カレンダーの予定の中身（タイトルなど）を返してよいのは、**その予定の持ち主本人のリクエストに対してだけ**。ほかの家族には一切返さない。このタスクでは、ほかの家族向けの表示（斜線の「予定あり」）は作らない。
- 個人予定は D1 に保存しない。サーバー側でキャッシュもしない。ログにも出さない。
- 個人予定の取得は、必ずリクエストした本人のトークンで行う。ほかの人のトークンで個人カレンダーを読むコードを書かない。
- 漏れていないことを確かめるテストを必ず書く（下の「テスト」）。

## スコープ（人間の作業が先に必要）

- 追加するスコープ：`https://www.googleapis.com/auth/calendar.events.readonly`（予定の読み取りのみ）。書き込みはしないので `calendar.events` は使わない。docs/03 と docs/06 に記録する。
- ログイン時には求めない。利用者が「自分の予定を表示する」を有効にしたときに、段階的認可（incremental authorization）で求める。家族 ACL の段階的認可と同じ仕組み（`oauth_states` の purpose を追加）を使う。
- Google Cloud 側のスコープ登録は人間が行う（この指示書を渡す時点で実施済みの想定）。PR の「未解決の点」に、staging での確認に必要な前提として書く。

### 再ログインで追加スコープが失われる問題の修正（このタスクに含める）

いまの通常ログインは `include_granted_scopes` を付けていないため、再ログインすると新しいリフレッシュトークンが基本スコープだけになり、追加で同意したスコープ（`calendar.acls`、今回の `calendar.events.readonly`）が保存値から消える。

- 通常ログインと招待付きログインにも `include_granted_scopes=true` を付け、Google が返したスコープの集合をそのまま保存する。
- 既存のスコープ検証（基本スコープがそろっていること）は維持する。
- テスト：追加スコープを持つ利用者が再ログインしても、保存されたスコープに追加分が残ること。

## データ

- `member_calendars` テーブルを追加する（docs/03 の案に沿う。合意済みの設計なので追加の確認は不要）。
  - 持つもの：メンバー ID、Google のカレンダー ID、表示対象かどうか。カレンダー名や予定の中身は保存しない（名前は表示のたびに `calendarList.list` から取得する）。
  - 対象は大人のメンバー本人の行だけ。メンバーや家族の削除に連動して消える。
  - Drizzle のスキーマ → `pnpm db:generate` で新しいマイグレーションを作る（既存のマイグレーションは編集しない）。

## API（`familySecurityMiddleware` を通す。入出力は共有の zod スキーマ）

- `GET /api/families/:id/personal-calendars`
  - 本人のトークンで `calendarList.list` を呼び、選択肢（ID、名前、主カレンダーかどうか、選択中かどうか）を返す。家族カレンダー自体は選択肢から除く。
  - 追加スコープが未同意なら、その旨を示す固定の状態を返す（エラーにしない）。
- `PUT /api/families/:id/personal-calendars`
  - 本人の選択を一括で置き換える。選べる数に上限を設ける（例：10）。本人の `calendarList` に存在する ID だけを受け付ける。
  - 追加スコープが未同意なら、段階的認可の URL を返す（招待発行と同じ形）。同意後の戻り先は `/family`。
- `GET /api/families/:id/week/personal?start=YYYY-MM-DD`
  - 週の範囲は家族の週 API と同じ計算（`getWeekRange`）。
  - 本人が選択したカレンダーの予定を、本人のトークンで `events.list`（`singleEvents=true`、`timeMin/timeMax`）して返す。
  - 返す項目は最小限：ID、タイトル（非公開などで取得できない場合は空）、時刻（終日／時刻指定）、繰り返しかどうか、どのカレンダーか。説明、場所、参加者、メールアドレスは返さない。
  - 本人が「欠席」と回答した予定は除く。参加者情報を読む場合も、スキーマには本人の回答状況だけを残し、メールアドレスを保持しない。
  - 未同意・未選択なら空の結果と状態を返す。一部のカレンダーだけ失敗した場合の扱いを決めて docs に書く（全体を失敗にするか、取得できた分だけ返して欠けたことを示すか）。
  - 家族の週 API（`/week`）のレスポンスには個人予定を**入れない**。家族の予定の取得と、個人予定の取得は、失敗しても互いに影響しないようにする。
- すべて、未ログインは 401、その家族の active メンバーでなければ 404。

## 画面

### 「家族」タブ（`/family`）

- 「自分の予定の表示」の欄を追加する。
  - 未同意：説明（自分の予定は自分の画面にだけ表示され、家族には見えないこと）と、「自分の予定を表示する」ボタン。押すと Google の同意画面へ進む（連打防止は招待発行と同じ）。
  - 同意済み：カレンダーの一覧をチェックボックスで選ぶ。初期状態は主カレンダーだけ選択。保存できる。
  - すべて外せば表示をやめられる。Google 側で権限そのものを取り消す方法も案内する。

### 週ビュー（S1）

- 自分の個人予定は、docs/02 の「自分の個人予定」の見た目で表示する：白背景、自分のメンバー色の点線枠、タイトル、鍵アイコン、「自分だけ」。
- 平日の行（compact）：個人予定は最大2件までチップで出し、残りは「ほか N 件」とする。タップでその日の全件を表示する。
- 「いつもと違う日」のカードと週末・祝日のカード：家族予定のリストに、時刻順で混ぜて表示する。
- 個人予定は日のレイアウト（compact / expanded / weekend-card）を変えない。レイアウトは家族全員で同じに保つ。
- 「ルーティンを隠す」は、繰り返しの個人予定にも適用する。
- 個人予定はタップしても編集画面を開かない（Danran からは変更しない）。
- 個人予定の取得に失敗しても、家族予定はそのまま表示し、個人予定の欄にだけ控えめな案内を出す。

## テスト

- **プライバシー**
  - 利用者 A の個人予定が、利用者 B のどの API レスポンスにも含まれないこと（`/week`、`/week/personal`、`/personal-calendars`）。
  - `/week/personal` が、リクエストした本人のトークンだけを使うこと（Google へのリクエストの Authorization を検証する）。
  - レスポンスに説明・場所・参加者・メールアドレスが含まれないこと。
  - D1 に予定のタイトルが保存されないこと。
- API：未同意・未選択・選択あり、他人の選択を変更できないこと、`calendarList` にない ID の拒否、上限、欠席の除外、終日・複数日・日またぎ、ページング、Google の失敗の分類、一部失敗時の扱い。
- 段階的認可：同意前後の流れ、キャンセル・失敗時の戻り先、再ログイン後もスコープが残ること。
- Playwright（API をモック）：有効化からカレンダー選択まで、週ビューでの表示（「自分だけ」、平日の「ほか N 件」、ルーティンを隠す）、個人予定の取得失敗時に家族予定が残ること、390px と 445px。
- 既存のテストがすべて通ること。

## 受け入れ基準

- 自分の個人予定が、自分の週ビューにだけ「自分だけ」として表示される。
- ほかの家族の画面・API には、その予定の情報が一切出ないことがテストで保証されている。
- 追加スコープは、利用者が有効にしたときに初めて求められる（ログイン時には求めない）。
- `pnpm typecheck` / `lint` / `test` / `e2e` が通る。`pnpm db:generate` で差分が残らない。
