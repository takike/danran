# タスク 2-2：空き状況に使うカレンダーの選択と、追加の同意

- ブランチ名: `phase2/2-2-busy-calendars`（最新の main から分岐）
- 作業前に読むもの: [AGENTS.md](../../AGENTS.md)（特に「絶対に守ること」1）、[docs/01-concept.md](../01-concept.md)（原則2「既定はプライベート、共有は明示的に」）、[docs/03-architecture.md](../03-architecture.md)（① 個人カレンダー、スコープ、`member_calendars`）、[docs/10-authentication.md](../10-authentication.md)（段階的認可）、[docs/18-personal-events.md](../18-personal-events.md)（同じ形の先行実装）
- **人間の確認が必要**（スコープの追加、個人カレンダー、認証、マイグレーションを含む）

## 目的

大人のメンバーが、「自分の予定がある時間帯を家族に共有する」ことに同意し、どのカレンダーを空き状況に使うかを選べるようにする。**このタスクは同意と選択の保存まで。** 実際に空き状況を取得して返す API は次のタスク（2-3）、週ビューへの表示はその後（2-5）で作る。

## プライバシー（最優先）

- このタスクでは、ほかのメンバーの個人カレンダーを読むコードを書かない。`freeBusy.query` も呼ばない。
- 選択の一覧（カレンダーの名前・ID）を返してよいのは、**本人のリクエストに対してだけ**。ほかのメンバーが、誰がどのカレンダーを選んだかを知る手段を作らない。
- 保存するのは、本人が選んだカレンダーの ID と、用途のフラグだけ。カレンダー名や予定の中身は保存しない。選んでいないカレンダーの行は作らない。
- 漏れていないことを確かめるテストを必ず書く（下の「テスト」）。

## スコープ

- 追加するスコープ：`https://www.googleapis.com/auth/calendar.freebusy`（予定の有無だけを読む）。docs/03 と docs/06 に記録する。
- ログイン時には求めない。利用者が「空き状況を家族に共有する」を有効にしたときに、段階的認可で求める。`personal-events` と同じ仕組みで、`oauth_states` の purpose に `free-busy` を足す。`include_granted_scopes=true` と `login_hint` も同じように付ける。
- 同意後の戻り先は `/family`。成功・拒否・失敗・アカウント違いの戻り先は、`personal-events` と同じ形で、区別できる固定の値にする（例：`/family?busy=granted`、`/family?error=busy_denied` など）。
- Google Cloud 側のスコープ登録は人間が実施済み（2026-10-05 に確認）。

## データ

- `member_calendars` に列 `include_in_busy`（真偽、既定 false、NOT NULL）を足す。Drizzle のスキーマ → `pnpm db:generate` で**新しいマイグレーション**を作る。既存のマイグレーションは編集しない。既存の行は消さず、書き換えない（既定値で false になる）。
- 行の意味：`display_enabled`（本人の画面に予定を表示する。タスク 2-1）と `include_in_busy`（空き状況に使う）は独立。どちらかが true の行だけを持つ。両方 false になった行は削除する。
- 1人が空き状況に選べるカレンダーは最大10件。

## API（`familySecurityMiddleware` を通す。入出力は共有の zod スキーマ）

- `GET /api/families/:id/busy-calendars`
  - 本人のトークンで `calendarList.list` を呼び、選択肢（ID、名前、主カレンダーかどうか、空き状況に選択中かどうか）を返す。家族カレンダー自体は選択肢から除く。
  - 追加スコープが未同意なら、その旨を示す固定の状態を返す（エラーにしない）。
  - 保存した選択がないときは、**すべて未選択**で返す（主カレンダーを選択済みにしない）。保存した選択があるかどうか（`hasSavedSelection`）も返す。
- `PUT /api/families/:id/busy-calendars`
  - 本人の空き状況の選択を一括で置き換える。本人の `calendarList` に存在する ID だけを受け付ける。上限10件。
  - 追加スコープが未同意なら、段階的認可の URL を返す（`personal-calendars` と同じ形）。
  - **`display_enabled` を変えない。** 逆に、既存の `PUT /personal-calendars` は `include_in_busy` を変えないように直す（いまは本人の行を全削除して入れ直しているので、そのままだと空き状況の選択が消える）。この点はテストで固定する。
- どちらも、未ログインは 401、その家族の active な大人のメンバーでなければ 404。

## 画面（`/family`）

- 「自分の予定の表示」の欄の下に、「空き状況の共有」の欄を足す。
  - 説明：家族に伝わるのは「予定がある時間帯」だけで、予定のタイトルや内容は伝わらないこと。選んだカレンダーの ID だけを保存すること。
  - 未同意：「空き状況を家族に共有する」ボタン。押すと Google の同意画面へ進む（連打防止は「自分の予定の表示」と同じ）。
  - 同意済み：カレンダーの一覧をチェックボックスで選んで保存する。**初期状態はすべて未選択**で、「現在、空き状況は共有していません。共有するカレンダーを選んで保存してください。」と出す。何も選ばず保存済みの選択もないときは、保存ボタンを押せない。
  - すべて外して保存すれば共有をやめられる。
  - 案内文：会社の Google カレンダーの予定も空き状況に含めたい場合は、会社のアカウント側で自分の個人アカウントに「予定の有無のみ」を共有すると、この一覧に現れること（会社の設定で外部共有が禁止されている場合はできないこと）。
- 未保存の選択があるときの PWA 更新の保留（`useReloadProtection`）は、「自分の予定の表示」と同じ扱いにする。

## 変えないもの

- 「自分の予定の表示」の画面の見た目と挙動、`/week/personal`、週ビュー。
- `personal-events`・通常ログイン・招待ログイン・`family-acl` の認可の流れと戻り先。
- 家族の週 API（`/week`）。
- 既存のマイグレーションファイル。
- Google のアクセストークンの取得方法（リクエストごとの更新は既知の課題で、このタスクでは直さない）。

## テスト

- **プライバシー**
  - 利用者 A の空き状況の選択（カレンダーの ID・名前）が、利用者 B のどの API レスポンスにも含まれないこと（`/busy-calendars`、`/personal-calendars`、`/week`、`/week/personal`）。
  - `/busy-calendars` が、リクエストした本人のトークンだけを使うこと（Google へのリクエストの Authorization を検証する）。
  - 保存後の `member_calendars` に、選んでいないカレンダーの ID が無いこと。
  - このタスクで `freeBusy.query` が一度も呼ばれないこと。
- **2つの選択の独立**
  - `PUT /busy-calendars` で `display_enabled` が変わらないこと。`PUT /personal-calendars` で `include_in_busy` が変わらないこと。
  - 同じカレンダーを両方に選んだ場合、片方だけに選んだ場合、片方を外して両方 false になった行が削除されること。
- API：未同意・未選択・選択あり、他人の選択を変更できないこと、`calendarList` にない ID の拒否、上限、すべて外す、Google の失敗の分類。
- 段階的認可：同意前後の流れ、拒否・失敗・アカウント違いの戻り先、`login_hint`、`personal-events` のスコープを持つ利用者が `free-busy` に同意しても既存のスコープが残ること、再ログイン後も残ること。
- マイグレーション：既存の `member_calendars` の行が残り、`include_in_busy` が false になること。
- Playwright（API をモック）：有効化からカレンダー選択・保存まで、初期状態がすべて未選択で保存ボタンが押せないこと、すべて外して保存、「自分の予定の表示」の欄が影響を受けないこと、390px と 445px。
- 既存のテストがすべて通ること。

## 受け入れ基準

- 大人のメンバーが、追加の同意をしたうえで、空き状況に使うカレンダーを選んで保存できる。
- 追加スコープは、利用者が有効にしたときに初めて求められる。
- 「自分の予定の表示」の選択と、空き状況の選択が、互いに影響しない。
- ほかのメンバーの選択が、API にも画面にも出ないことがテストで保証されている。
- `pnpm typecheck` / `lint` / `test` / `e2e` が通る。`pnpm db:generate` で差分が残らない。
