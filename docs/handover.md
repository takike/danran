  3. 振り替えていない通常の回は、これまでどおりグレーのチップで出る。「ルーティンを隠す」で、通常の回は消え、振り替えた回は残る。

## 4. 仕組みの要点（レビューで前提になること）

- **3層のデータ**：① 個人カレンダー（中身は持たない。他人には busy の区間だけ）、② 家族カレンダー（アプリが作った共有 Google カレンダーが正）、③ アプリ固有データ（D1）。
- **家族カレンダーの共有**：`calendar.app.created` だけでは共有設定ができないため、オーナーが招待リンクを発行するときだけ `calendar.acls` を追加で同意してもらう。参加した大人は、自分のトークンで家族カレンダーを読み書きできる。
- **予定の付加情報**：対象メンバー・担当・候補/確定は Google のイベントの `extendedProperties.private` を正とし、持ち物だけ D1 の `event_meta` で補う。
- **Google と D1 は同じトランザクションにできない**。作成は決定的なイベント ID で二重作成を防ぎ、途中失敗は同じ操作の再試行で回復する。
- **OAuth コールバックの失敗**は、生の JSON ではなく固定の同一オリジンパスへのリダイレクトで返す（docs/10）。
- **PWA の更新**：新しい Service Worker が制御を引き継ぐと自動で1回再読み込みする。入力中は `useReloadProtection` で保留し、バナーを出す。

## 6. これまでに学んだこと

指示書を書くとき・レビューするとき・人間と話すときに効いたこと。

- **指示は Codex に字義どおり広く適用される。** 変えてほしくない既存の挙動は、指示書に「変えない」と書く。レビューでは、指示にない挙動の変化を探す。
- **Codex は以前、レビュー前に自分でマージしていた**（PR #3〜#10）。AGENTS.md と各指示書に「PR を作成したら止まる」と明記してからは守られている。毎回、勝手にマージされていないか確認する。
- **fetch のモックでは Google の実際の挙動は分からない。** PR #17 では、`events.patch` が入れ子のオブジェクトをマージする仕様（終日と時刻指定の切り替えで失敗する）をレビューで指摘した。実 API の仕様を自分で考え、実機確認の手順に入れる。
- **不具合報告の多くは、タイミングか表示の遅れだった。** マージ直後の 404 はデプロイ未完了、「設定が見つからない」もデプロイ完了前、「Google カレンダーから消えない」はスマホのアプリの同期遅れ。コードを疑う前に、Actions の実行状況と、サーバー側の実際の状態を確認する。
- **実機でしか分からないことがある。** 390px 固定の幅が実機（445px）で細く見える、「予定なし」が並んで平日が目立つ、各日の「追加」ボタンがうるさい、など。スクリーンショットは必ず見て、実機確認の結果も聞く。
- **長い指示はチャットで渡せない**（Termius で貼ると落ちる）。指示書はリポジトリに置き、チャットは1行にする。
- **人間は推奨を求めることが多い。** 選択肢を並べるより、推奨と理由を示し、計画にない判断をしたときは最後に明記する。
- **画面の PR は、スクリーンショットを目で見るだけでなく、気になる箇所は実際のブラウザで測る。** PR #25 では、予定のブロックが実際の時間より長く描かれていること（最小の高さ 68px）を、1回目のレビューで見落とした。画素を数え、レビュー用の作業ツリーで一時的なテストを足して高さを測って確かめた（測ったあとは元に戻す）。
- **スクリーンショットに写っていない状態は、レビューで見落とす。** PR #28 では、振替のフォームを開いた状態が写っておらず、「保存」ボタンが白地に白い文字になっているのを実機確認まで見つけられなかった。フォームや展開した状態など、主要な操作の画面は、指示書でスクリーンショットに含めるよう指定する。写っていない主要な状態は、レビュー用の作業ツリーで自分で開いて確かめる。
- **見た目の指示は、数値で書く。** 「読める最小の高さ」「狭くなったら」のような書き方は、広く解釈される。PR #25 は、それが原因で修正依頼が3回になった（最小の高さ、タイトルだけにする条件）。
- **プロンプトの書き方が原因の手戻りは、そう伝える。**（例：PR #12 で、同意キャンセル時の戻り先まで失敗用の画面に統合された。）
